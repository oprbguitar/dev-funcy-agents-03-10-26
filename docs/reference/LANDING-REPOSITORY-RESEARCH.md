## Admisión de reutilización en un producto

La decisión de esta investigación es documental, no aprobación de incorporar paquetes. Antes de `ADOPT`/`ADAPT`, registra repo, SHA, ruta/texto exacto de licencia, copyright, componente/asset utilizado, modificaciones, dependencias, licencia de fuentes/imágenes/iconos, uso comercial, redistribución, compatibilidad, mantenimiento, vulnerabilidades conocidas, fecha y revisor. Conserva avisos exigidos. Distingue implementación original de copia o derivación.

Selecciona una base mínima acorde con tecnología, contenido, accesibilidad, coste y mantenimiento. Compara bloques estáticos, componentes o configuración; no agregues nueve frameworks. Si licencia falta, es ambigua o incompatible, mantén `INSPIRE_ONLY` o `REJECT` hasta resolverlo. GPL/AGPL y CC BY-NC exigen análisis específico; público no significa libre para todo uso.

Los SHA fijan el texto observado, no certifican build, seguridad, accesibilidad, rendimiento, ausencia de vulnerabilidades o derechos de todos los assets. Esos checks permanecen `NOT_RUN`. Antes de adoptar, repite revisión sobre la versión que realmente se incorporará. Este documento no cambia la licencia de EOS.

## Procedimiento de selección contextual e integración incremental

1. **Perfilar destino.** Registrar nuevo/existente, público y tarea, modo `operate/read/persuade/explore/experience`, idioma, densidad, marca aprobada, navegación, framework/versiones, hosting/runtime, presupuesto, formularios, datos y dispositivos. En ADOPT inspeccionar UI renderizada, `DESIGN.md`, tokens, componentes, métricas disponibles y flujo crítico antes de cambiar. Para esta biblioteca documental la landing es `NOT_APPLICABLE`; ampliar referencias no crea un frontend.
2. **Comparar al menos tres estructuras.** Ejemplo orientativo: página editorial de contenido con CTA; demostración guiada de flujo/producto; catálogo de servicios con navegación por necesidad. No cuentan tres paletas de la misma composición. Evaluar ajuste a tarea, claridad, accesibilidad, responsive, coste de mantenimiento y carga del cliente; justificar selección y descartes sin inventar puntuaciones medidas. Cero dependencias nuevas es una opción válida.
3. **Elegir alcance mínimo.** Para sitio estático nuevo, contrastar Landwind/HTML con AstroWind o Astroship; para React existente, contrastar implementación local con piezas de Launch UI o Cult UI; para formulario operativo, evaluar primitivas existentes y coss por rutas licenciadas. Son ejemplos condicionales, no recetas por marca ni autorización de migrar. No importar React en una página estática solo por un efecto. Un despliegue SSR necesita runtime/adaptador compatible; un nombre de framework no demuestra compatibilidad con el hosting.
4. **Aplicar Pierre antes del código visual.** Cargar `pierre-design-director` del host; en el producto destino ejecutar `node ~/AI-Design-Harness/bin/design-pick.mjs --project "<destino>" --mode <modo> --domain "<dominio>"`. Registrar dirección y tokens antes de componer. Mantener identidad del proyecto encaminado; justificar cualquier desviación funcional del selector. Sin Node/FS, declarar la dirección manual en seis líneas antes del código. La biblioteca de componentes acelera implementación; Pierre conserva la dirección visual.
5. **Admitir cada fragmento.** Verificar origen/cambios de propietario, commit inmutable, texto de licencia por archivo y assets, avisos, patentes/copyleft/redistribución, conflictos de licencia, dependencias y scripts ejecutables, mantenimiento y vulnerabilidades. Decidir `INSPIRE_ONLY | ADAPT | ADOPT | REJECT` con responsable y evidencia. Aquí todos siguen como referencia `INSPIRE_ONLY`, salvo exclusiones explícitas previas. Pendiente de licencia impide copiar; no impide diseñar una alternativa original.
6. **Integrar un incremento reversible.** Conservar rutas, contratos, autenticación, datos, identidad, contenido real y componentes útiles del destino. Separar refinamiento de rediseño; registrar baseline, cambios y rollback. Evaluar solo los paquetes necesarios, sin instalar los 25 ni clonar en lote. Degradados, glassmorphism, bento, 3D, cursor magnético y motion no son requisitos. Incluirlos solo si mejoran una tarea comprobable; una buena demo no acredita UX.
7. **Verificar el producto real.** Correr pruebas apropiadas al alcance, teclado/foco/contraste, estados, carga/errores, 360/768/1280/1600 px, `prefers-reduced-motion`, CTA/formularios, presupuesto de JS/imágenes y medición con herramienta/contexto registrados. Revisar tráfico y almacenamiento antes de activar analytics o embeds. Ejecutar `node ~/AI-Design-Harness/bin/design-lint.mjs .` en el destino y corregir RECHAZADO. Build aprobado no reemplaza inspección del navegador.
8. **Documentar y cerrar.** Actualizar `DESIGN.md` para frontend sustancial, brief y estado vivo canónicos, archivos/adaptaciones, licencias/avisos, pruebas y limitaciones; registrar dirección sustancial con `design-log.mjs` del harness cuando corresponda. Una comparación documental no necesita generar historial visual ficticio. Publicar solo dentro de autorización existente; ninguna sugerencia comercial del adjunto activa campañas, modelos, proveedores o seguimiento.

Revisar este catálogo al seleccionar una pieza, ante transferencia/archivo/cambio de licencia o una alerta que afecte al commit adoptado. El responsable del producto mantiene su inventario de componentes; EOS mantiene el procedimiento. No se promete conformidad ISO, cumplimiento jurídico, seguridad ni conversión por elegir una plantilla.
